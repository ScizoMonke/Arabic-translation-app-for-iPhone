It ships a prebuilt llama.xcframework (ios-arm64 + macos, Metal embedded) as a release asset; docs/xcframework.md shows the SwiftPM binaryTarget pattern. So: app/LlamaBinary/Package.swift, a local package with one binaryTarget "llama" (url + sha256 of llama-b12020-xcframework.zip), wired by XcodeGen as a local package. No ggml compile on the runner.

6. Likely break 1: SwiftPM/Xcode not extracting the nested build-apple/llama.xcframework from the zip, or the dynamic llama.framework not embedded in the .app (dyld crash at launch). Mitigation: SwiftPM 6.2 stripFirstLevel read in source; workflow asserts Frameworks/llama.framework exists in the .app.
7. Likely break 2: C import shapes in Swift (OpaquePointer vs UnsafeMutablePointer, C enum constants like LLAMA_LOAD_MODE_MMAP, implicitly unwrapped returns). Mitigation: every symbol checked against include/llama.h at b12020 and against the upstream llama.swiftui example's own usage.
8. Likely break 3: task_info / TASK_VM_INFO and os_proc_available_memory spelling in Swift, and Swift 6.2 isolation diagnostics around the new queue-backed engine. Mitigation: engine is @unchecked Sendable with all state on one queue; memory probe uses the documented mach pattern.
9. Runtime risks (not compile): memory near the ~6 GB ceiling (R10), first Metal shader compile on load, Arabic script leaking into the arabizi field (bench prompt C: 44 chars over 40 rows) which is refused rather than half-shown.
